Technical walkthrough / rust-learning / § sharing states, part 1

Can one thread read
another thread's stack?

Physically yes, logically no. Threads of one process share a single address space, so a stack is just ordinary memory at an ordinary address — nothing in the hardware stops the read. What stops it is Send, Sync and the 'static bound on thread::spawn. This note takes both halves apart, measures the address space, breaks the rule on purpose with a raw pointer, and then shows the one legal way to share a stack frame: thread::scope.

The short answer

A thread's stack is not protected by the hardware. It sits in the same address space as every other thread's stack, at a plain address any thread can dereference. Stacks are private by a convention the compiler enforces — the 'static bound on thread::spawn — not by the MMU. Break that convention with a raw pointer and the read works; it is simply undefined behaviour the moment the frame dies or the access races. thread::scope is the escape hatch that makes stack sharing legal, because it can prove the frame outlives the threads.

§ 1One address space, several stacks

A process owns exactly one address space; a thread owns a stack, a register set and its TLS block, and takes everything else from the process. So "the stack of thread 2" is not a separate memory domain — it is a range of pages inside the same page table thread 1 is already using. The kernel allocates it with mmap when the thread is created, and unmaps it when the thread dies.

That is easy to see rather than assume. The program below prints one address from each region while three spawned threads are all still alive:

§ 2Doing it anyway: the raw-pointer route

To prove the point, send the address rather than the reference. A usize is Send and carries no lifetime, so the borrow checker has nothing to object to — the type system has been routed around, deliberately.

// lessons/sharing_states_part_1/src/main_read_from_stack.rs
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();

    let t = thread::spawn(move || {
        let x = 42_i32;                          // on thread 2's stack
        tx.send(&x as *const i32 as usize).unwrap();  // leak the address as a plain integer
        thread::sleep(Duration::from_millis(100));
        println!("[child]  after parent's write, x = {}", x);
    });

    let addr = rx.recv().unwrap();
    unsafe {
        let p = addr as *mut i32;
        println!("[main]   read  *p = {}", *p);
        *p = 999;                                  // and write it, too
    }
    t.join().unwrap();
}
$ rustc -O main_read_from_stack.rs && ./main_read_from_stack
[child]  &x = 0x16fb2ee24   value = 42
[main]   &y = 0x16f9266e4   ← main's own stack, 2 MiB away
[main]   received address 0x16fb2ee24
[main]   read  *p = 42              ← thread 1 read thread 2's stack
[main]   wrote *p = 999
[child]  after parent's write, x = 999   ← and thread 2 observed the change

Fig. 3 — it works. measured Not merely a read: a write from another thread mutated a local variable that the owning thread still considered its own. Note this survived -O — the optimiser happened to keep x in memory. It was under no obligation to.

What is wrong with it

The program prints the "right" answer and is still undefined behaviour on two independent counts. Aliasing: x is a local the compiler believes it exclusively owns, so it may keep it in a register, fold it to a constant, or reorder around it — the write through *p is then simply lost. Data race: two threads touch the same location with no synchronisation between the write and the child's read; the sleep is a hope, not a happens-before edge. UB does not mean "crashes"; it means the compiler's assumptions and yours have diverged and nothing is owed to you afterwards.

§ 3What the compiler actually forbids

In safe code the door is shut by one bound in the signature of spawn:

// library/std/src/thread/mod.rs
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,

Fig. 4 — the whole mechanism. source Send says the closure may cross a thread boundary. 'static says it holds no borrow of anything shorter-lived than the program — which is exactly what a reference into a stack frame is. The compiler cannot prove the parent's frame outlives the child, so it refuses.

fn main() {
    let x = 5;
    thread::spawn(|| println!("{}", x));   // borrows main's stack
}
error[E0373]: closure may outlive the current function, but it borrows `x`,
             which is owned by the current function

Fig. 5 — the refusal. measured "May outlive" is the whole argument. Nothing here is about permission or privacy; it is about lifetime. This is the exact bug class that C hands you silently — a pointer to a stack frame that returned.

So safe code is left with two options, and both avoid the parent's stack entirely: move ownership into the closure, or put the data on the heap under shared ownership — Arc<T> for read-only, Arc<Mutex<T>> for mutation. The Mutex in this lesson's main.rs is the second half of that answer: heap placement solves lifetime, the mutex solves simultaneity. Neither is needed for a stack, because a stack cannot be shared in the first place — unless you ask for a scope.

§ 4The legal exception: thread::scope

Since Rust 1.63 there is a way to hand a real stack borrow to another thread. thread::scope cannot return until every thread spawned inside it has been joined — the implementation joins them, and joins them even on unwind. That turns "may outlive" into "provably does not outlive", so the 'static bound is dropped and &T into the parent frame becomes legal.

fn main() {
    let x = 5;                          // main's stack
    println!("[main]  &x = {:p}", &x);

    thread::scope(|s| {
        s.spawn(|| println!("[t1]    x = {} at {:p}", x, &x));   // no `move`, a real borrow
        s.spawn(|| println!("[t2]    x = {} at {:p}", x, &x));
    });                                 // implicit join of both threads happens here

    println!("[main]  x still alive: {}", x);
}
[main]  &x = 0x16f2a6878
[t1]    x = 5 at 0x16f2a6878   ← same address
[t2]    x = 5 at 0x16f2a6878   ← same address
[main]  x still alive: 5

Fig. 6 — a stack read across threads, in safe code. measured Both children print main's address, not a copy: the borrow is genuine and no heap allocation is involved. This is the answer to the title question in its useful form — yes, via scope, checked at compile time.

The price is structural, not syntactic: a scoped thread cannot outlive the scope. If a thread must keep running after the function returns, or be stored in a struct, or be detached, scope is the wrong tool and the data belongs on the heap. Shared mutation still needs a lock or an atomic — scope relaxes the lifetime rule only; the aliasing rules are untouched, so two &mut to the same local remain rejected.

§ 5Why the unsafe version is not merely "unidiomatic"

The temptation after § 2 is to conclude the raw-pointer trick works and the rules are bureaucracy. So here is the same trick with one change: the address escapes from a function that returns, and the thread keeps running. The frame is dead and its bytes are recycled.

fn leak_addr(tx: mpsc::Sender<usize>) {
    let secret = 0xDEADBEEF_u32;
    tx.send(&secret as *const u32 as usize).unwrap();
}                                         // frame dies here — address now dangles

let t = thread::spawn(move || {
    leak_addr(tx);
    let _junk = [0x41414141_u32; 64];      // reuse the same stack region
    thread::sleep(Duration::from_millis(200));
});
let addr = rx.recv().unwrap();
unsafe { println!("[main] 0x{:x} -> 0x{:X}", addr, *(addr as *const u32)); }
[main] read dead frame at 0x16fc8ed14 -> 0x0

// not 0xDEADBEEF. not 0x41414141. no crash, no warning, no signal.

Fig. 7 — silent garbage. measured The address is still mapped, so there is no segfault to alert anyone; the read simply returns whatever now occupies those bytes. In a longer-lived program that region would hold another frame's live data — which is how a stack-address leak becomes an information-disclosure bug rather than a crash.

Worth knowing how weak the tooling is here. The § 2 program was rebuilt with ThreadSanitizer (-Zsanitizer=thread with -Zbuild-std) and run repeatedly:

Fig. 8 — three clean runs of a program that is UB. measured TSan reports races it happens to observe, and the sleep spaced the accesses far enough apart that it saw nothing. Take the lesson at face value: a green test run is not evidence that cross-stack pointer traffic is sound.

§ 6Summary

Table 1 — the three ways to get data into another thread
RouteWhere the data livesChecked byThread may outlive the parent frameVerdict
move into spawn moved into the child's stack / closure the type system, Send + 'static yes the default; nothing is shared, so nothing can race
Arc<T> · Arc<Mutex<T>> heap, shared ownership Send / Sync + the lock at runtime yes the general answer for shared mutable state
thread::scope the parent's stack, borrowed the borrow checker, no 'static needed no — joined at the end of the scope the only sound way to read another thread's stack
usize + raw pointer the parent's stack, unchecked nothing yes, and that is the bug UB: aliasing violation and data race

Reading the table. The fourth row is not a faster version of the third. It is the third row with the proof deleted.

  1. 01The hardware does not help Threads share one page table. A stack address from thread 2 is a perfectly valid address in thread 1. Isolation exists between processes; between threads there is only the type system.
  2. 02'static is the wall thread::spawn rejects stack borrows because it cannot prove the frame outlives the thread. That is a lifetime argument, not a permission one.
  3. 03scope supplies the missing proof Guaranteed join at the end of the block means the frame provably survives, so safe stack sharing becomes possible — at the cost of the threads not being allowed to escape.
  4. 04Working is not sound The raw-pointer version printed the expected value under -O and produced no sanitizer warning in three runs. It is still UB. This is precisely the class of bug the Send / Sync / 'static triad exists to make unrepresentable.
