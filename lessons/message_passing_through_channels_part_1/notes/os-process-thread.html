The short answer

A program is a file on disk; it does nothing. A process is a program loaded into an address space of its own; it is the unit of isolation. A thread is a point of execution inside a process; it is the unit of scheduling. One program usually has one process and anywhere from one to several thousand threads. The kernel does not schedule processes: it schedules threads.

§ 1Four entities and one confusion

In everyday speech "program", "process" and "thread" are used interchangeably, but they are objects of entirely different natures: one lives in the file system, another in a page table, the third in a scheduler queue. Let us sort them out by asking "what physically exists".

The key distinction. A process answers the question "which memory is visible", a thread answers "which code is executing right now". These are orthogonal, which is why one address space happily holds many threads.

Which leads straight to a consequence that surprises many people: a process does not execute. It owns memory and permissions, but the scheduler never sees it. What queues up for a CPU core is threads. A process with no threads is a dead shell, and the kernel frees it immediately.

The special case: Linux

It is easy to draw the wrong conclusion here, so let us be blunt: Linux does have processes, and their address spaces are just as separate as anywhere else. Isolation is provided by the MMU, the mechanism is identical to macOS and Windows, and the experiment in § 2 gives the same result.

What is peculiar about Linux is something else: it does not store a "process" as a single indivisible object, but decomposed it into independently shareable resources. Scheduling lives in task_struct, the address space in mm_struct, the descriptors in files_struct, and so on. A process and a thread differ only in which of those structures are created anew and which are taken from the parent. It is all controlled by one set of flags to one system call:

Table 2 — process and thread on Linux: one flag apart
What you callWhat it becomesmm_struct (address space)What you get

without CLONE_VM		 a new one, a copy-on-write copy of the parent's A process. Its own heap, full isolation, its own TGID
pthread_create() clone(CLONE_VM | CLONE_THREAD | CLONE_FILES | CLONE_SIGHAND | CLONE_FS | ...) the very same one, the ->mm pointer is copied A thread. A shared heap, its own TID within the same TGID

Table 2 docs CLONE_VM is literally the "share the address space or not" switch. The remaining flags pick up the other items from Fig. 3: CLONE_FILES the descriptor table, CLONE_SIGHAND the signal handlers, CLONE_FS the cwd. "Process" and "thread" are just two conventional flag sets out of many possible ones; the kernel allows intermediate combinations too, and containers are the same processes plus namespace flags.

This model leaks out in exactly one place — the numbering — and that is the only real source of the "process or thread" confusion on Linux. In the kernel, "pid" means a task, that is, a thread:

  • getpid() returns the TGID (thread group id) — what everybody calls the process PID. It is the same for every thread of the process.
  • gettid() returns the task's own pid — what everybody calls the TID. It is unique per thread.
  • That is why kernel.pid_max limits tasks: 10,000 threads consume numbers just like 10,000 processes do. On macOS those counters are separate (kern.maxproc versus kern.num_taskthreads) — see Tables 4 and 5.
# inspecting a process's threads on Linux
$ ps                       ← one line per PROCESS (thread group)
$ ps -eLf                  ← one line per THREAD; the PID and LWP columns
$ ls /proc/<pid>/task/     ← one directory per thread
$ grep -E 'Tgid|^Pid|Threads' /proc/<pid>/status
Tgid:    4212      ← this is the "process PID" in the usual sense

Fig. 3 — the isolation boundaries. The heap is highlighted because it is the only shared source of mutable data of arbitrary size. The stack is private not because it is protected — another thread's stack address is technically reachable inside the process — but because it lives exactly as long as its frame does.

The proof

Both claims are verifiable in twenty lines. Below is the real output: a Box is moved into another thread and stays at the same address, then the same Box after fork() ends up at the same address but with different contents.

$ ./heap-demo
[threads]   main:   address 0x12b6062d0, value 111
[threads]   child:  address 0x12b6062d0 → same one? true, wrote 222   ← one heap
[processes] child  pid=9213: 0x12b606580 = 999
[processes] parent pid=9212: 0x12b606580 = 111   ← the child's write is NOT visible

Fig. 4 measured Note the second pair: the virtual address is literally identical, yet the data differs. That is copy-on-write — on the write, the kernel slipped a separate physical page under the child process while keeping the same virtual address. A virtual address only means something inside its own address space.

§ 3Stacks: where the sizes come from

A stack size is not one number but the outcome of three independent decisions made by different parties. They get mixed up constantly, so let us take them layer by layer.

  1. The main thread's stack is created by the kernel when the program is loaded. On Unix the size comes from RLIMIT_STACK (ulimit -s), on Windows from the SizeOfStackReserve field in the PE header — meaning the linker made the call. Program code can no longer change it.
  2. A new thread's stack is sized by default by the language runtime, not the OS. The OS value is almost always overridden.
  3. An explicit size — Builder::stack_size(), pthread_attr_setstacksize, dwStackSize. Rounded up to whole pages.

Why Rust always uses 2 MiB

This is not an operating system value but a decision by the std authors: Apple's 512 KiB and musl's 128 KiB were considered too cramped for recursive code and large frames. The constant sits right there in the sources and is the same for Unix and Windows:

library/std/src/sys/thread/unix.rs:31
#[cfg(not(any(target_os = "l4re", target_os = "vxworks",
              target_os = "espidf", target_os = "nuttx")))]
pub const DEFAULT_MIN_STACK_SIZE: usize = 2 * 1024 * 1024;

library/std/src/sys/thread/windows.rs:14
pub const DEFAULT_MIN_STACK_SIZE: usize = 2 * 1024 * 1024;

Fig. 5 source The cfg condition excludes only exotic targets like ESP-IDF — Linux, macOS, iOS, Android, BSD and Windows all land in the 2 MiB branch. The order of precedence: Builder::stack_size() → RUST_MIN_STACK → this constant.

$ ./stack-probe
main:             8372224 bytes = 7.98 MiB   ← 8176 KiB × 1024, matches ulimit -s
spawn() default:  2109440 bytes = 2.01 MiB   ← 2 MiB + pthread bookkeeping pages

$ RUST_MIN_STACK=524288 ./stack-probe
spawn() default:   536576 bytes = 0.51 MiB   ← the std constant really is overridable

Fig. 6 measured The third line of the first run shows that the requested 64 KiB turned into 76 KiB: a stack size is always page-aligned and gets a guard page.

More important than it looks

2 MiB is a virtual reservation, not occupied memory. The kernel hands out a range of addresses; physical pages are supplied only on first touch. A thread that made two function calls costs one or two pages — 16–32 KiB on arm64, not 2 MiB. So "12 thousand threads × 2 MiB = 24 GiB" is not a verdict: that much address space is reserved, but not consumed.

How many run at the same time

A separate question, and one that gets confused with the previous one. You can create 12287, but the number executing at any instant is exactly the number of hardware threads the CPU has. On this machine:

$ ./parallelism

§ 6Case study: why Chrome is 49 processes

Two browser windows are open. Activity Monitor shows a dozen rows named Google Chrome, and it is unclear whether those are processes or threads, and why there are so many. The reality is even further from expectations: it is not a dozen rows but 49 processes and 1232 threads — the list is simply sorted by memory and truncated, so 11 of the 49 are visible.

The confusion comes from three independent places, and it helps to separate them before looking at the numbers.

Table 6 — three sources of confusion

tab = process Not 1:1 in either direction: there can be more tabs than processes, and one tab can occupy several processes Chrome gives a process per site, not per tab. Five tabs of the same site → one process. But a tab with third-party iframes (ads, embedded videos) → several: every foreign site gets its own process (out-of-process iframes)
program = process One program deliberately launches dozens of processes That is an architectural decision in Chrome, not a leak and not a bug. Exactly what § 1 is about: a program is a file on disk, and you can make as many processes out of it as you like

Why do it this way

There is exactly one reason and it is all in § 2: a separate address space is the only guarantee the hardware provides. Threads inside a process provide no such guarantee at all: any thread can write to any byte of the shared heap, and one indexing bug in an image parser would corrupt the passwords from another tab. Three effects follow from this:

  • Crashes stay local. One renderer died — one tab died, not the browser. Exactly what Fig. 4 showed: a write in another process is not visible, because the MMU maps different physical pages under the same virtual address.
  • The sandbox. A renderer runs with almost no permissions: no files, no direct network access. Everything goes through IPC to the browser process, which vets the requests. Giving such restrictions to a thread is impossible — the permissions in § 2 are shared across the whole process, they are a property of it, not of a thread.
  • Parallelism. A side benefit, but a pleasant one: the scheduler spreads 49 processes across 16 cores by itself.

What it costs

Every process has its own heap, its own copies of the V8 and Blink structures, its own 26+ threads. Hence Chrome's reputation as a memory hog, and hence also the trap when reading Activity Monitor: the Memory column must not be summed. The binary's code, the framework, fonts and system libraries are mapped into all the processes at once and physically exist in a single copy — thanks to copy-on-write, the same mechanism as in Fig. 4. Adding up 49 rows counts those pages 49 times. What you should look at is system-wide Memory Pressure, not per-row arithmetic.

How to see the truth about tabs

Chrome has its own task manager: ⌥⇧Esc or Menu → More Tools → Task Manager. Unlike Activity Monitor, it knows which tab corresponds to which PID, and it lists extensions separately. It is the only way to see the "tab ↔ process" mapping — the operating system knows nothing about tabs, to it these are simply 42 processes with the same name.

In Activity Monitor it is worth enabling View → All Processes, Hierarchically — then the 49 rows fold into the tree from Fig. 9 and it becomes visible who is whose child.

How to read any task manager

Every row is a process, never a thread. The Threads column is how many threads live inside that row. One name across several rows means one program in several processes, not duplicates. Windows and tabs are not represented in this list at all: the OS knows nothing about them, the application invented them.

§ 7Where you hit a wall before the limit

All the numbers above are ceilings that real code almost never reaches. The Chrome from § 6 is one of the heaviest consumers on the system, and its 1232 threads amount to 10% of the macOS limit — and they are spread across 49 processes rather than collected in one. Other things get in the way, in the order in which they bite:

  1. 1st Context switching Hundreds of nanoseconds per switch, plus cache and TLB misses. With thousands of active threads the CPU is busy shuffling registers rather than doing your work. This bites at tens or hundreds of threads, not at thousands.
  2. 2nd Contention for memory and locks There is one heap per process. The allocator copes with per-thread caches (magazines in libmalloc, tcache in jemalloc), but those are still partitions of one heap, not separate heaps — an address from one thread is valid in any other. A shared mutex turns N threads into one.
  3. 3rd Stack pages actually touched The reservation is lazy, but deep recursion or big arrays on the stack commit pages for real. A thousand threads that each ate 200 KiB of stack is 200 MiB of honest RAM.
  4. 4th And only then — the kernel limit EAGAIN on the 12287th thread. By that point the program has long been unusable for the reasons above.
This is where async grows from

Async runtimes (tokio, async-std) exist precisely because of item 1. They hold 100,000 tasks on 16 OS threads: a task is a state machine in the heap a few hundred bytes in size, not a thread with a stack and an entry in the scheduler. Switching between them is an ordinary function call, with no kernel involvement. You need a thread where the work computes; a task where the work waits.
