§00 Address space overview

Before looking at references specifically, place the two regions they point into. A running Rust program's address space is roughly three zones: a stack that grows and shrinks automatically as functions are called and return, a heap that grows on demand through the allocator, and a fixed static / read‑only region — compiled functions, string literals, vtables — that never moves and needs no allocator at all.

§01 A reference is a ruled pointer

Physically, &T and *const T are the same bit pattern: one machine word holding an address. What makes a reference different is everything the compiler statically guarantees about it — none of which costs a single instruction at runtime:

  • never null, never dangling, always aligned — for its entire lifetime;
  • always points at a live, initialized value of type T;
  • aliasing XOR mutability: at any moment, either any number of &T or exactly one &mut T — never both;
  • no runtime tag, no refcount — the checking happens once, at compile time, then the reference is gone from the generated code, leaving only the raw address.

Same bytes, different contracts. A raw pointer is what a reference downgrades to when you tell the compiler "trust me" — see lessons/learn_pointers for that side of the fence.

§02 Binding mutability × reference mutability

Every reference has two independent mutability knobs, and it's easy to conflate them: whether the variable holding the reference can be reassigned, and whether the reference itself grants write access to what it points at. Four combinations, straight from the lesson file: 

let mut vec_1 = vec![1, 2, 3];
let mut vec_2 = vec![4, 5, 6];

let mut reference = &vec_1;   // mut binding, immutable reference
reference = &vec_2;             // ok: repoint the variable

let mut reference = &mut vec_1; // mut binding, mutable reference
reference.push(10);              // ok: mutate through it
reference = &mut vec_2;         // ok: repoint it too

§03 Mutating through &mut can move the heap data

reference.push(10) doesn't touch reference itself — it dereferences to the Vec header and calls push on it. If there's spare capacity, the new element lands in the existing buffer. If not, the Vec asks the allocator for a bigger buffer, copies the old elements over, frees the old buffer, and rewrites its own ptr and cap fields — all while reference's 8 bytes never change.

§04 Double indirection: a reference to a reference

The lesson's last two cases nest a reference inside another: 

let reference = &mut &vec_1;      // immutable binding of a &mut to a &
*reference = &mut &vec_2;             // ok — writes through the &mut
// reference = &mut &vec_3;               // ← would NOT compile: binding is immutable

reference here is a &mut &Vec<i32>: an 8‑byte pointer whose pointee is itself an 8‑byte reference slot. That inner slot is what actually points at a Vec header. Three hops before you reach anything resembling the numbers 1, 2, 3.

§05 Anatomy of a heap‑backed value

References borrow from something; that something has to live somewhere. For Vec<T> and String, the owning value is a small fixed‑size header — { ptr, len, cap }, 24 bytes on a 64‑bit target — and that header can sit anywhere (usually the stack). The header's ptr field is the only thing that actually points into the heap.

Owning typeStack representationSizeHeap payload
Box<T>{ ptr }8 Bexactly one T
Vec<T>{ ptr, len, cap }24 Bcontiguous T buffer
String{ ptr, len, cap }24 BUTF‑8 byte buffer (Vec<u8> underneath)

A reference to any of these — &Vec<T>, &String, &Box<T> — is a plain 8‑byte pointer at the header, not at the heap buffer directly. Getting to the actual bytes always costs one extra hop through that header.

§06 Thin pointers vs. fat pointers

Not every reference is one machine word. Referring to something whose size isn't known just from its type — a slice, a str, a trait object — needs a second word riding along with the address. Rust calls these fat pointers.

§07 Why lifetimes exist

A reference carries no runtime information about how long it's valid for — lifetimes are erased before codegen. All the safety comes from a compile‑time check that a reference's scope never outlives the stack frame (or heap allocation) that owns the data it points at. 

fn dangling() -> &Vec<i32> {
    let v = vec![1, 2, 3];  // v's header lives in this frame
    &v                          // ← compile error: v is dropped right here
}
Heap data doesn't get a free pass either: it just changes who can invalidate a reference. A stack frame is reclaimed on return; a heap buffer is freed when its owner (the Vec, the Box) is dropped or reallocates — both are lifetime events the borrow checker tracks the same way.

"Usually" is doing real work in that table — a reference is itself just a value, so nesting it inside a Vec<&T> or a Box<&T> moves the pointer's own 8 bytes onto the heap too. What never moves is what a reference borrows against: someone else's data, owned by a Box, a Vec, a plain local, or 'static storage — a reference itself owns nothing. For shared or runtime‑checked ownership instead of borrow‑checked exclusivity, that's Rc/Arc and RefCell territory, covered in their own lessons.
